# Architecture planning evaluation — issue #364

## Problem

The #361 and #362 instruction changes do not establish that future feature plans
choose coherent ownership or finish migrations. Earlier Python probes were small
and sometimes inconclusive. This evaluation reads design decisions under matched
inputs across the first four language families without treating prescribed prose
as success.

## Scope

Use five frozen case packets, one fresh baseline and one fresh revised context
each: ten attempted runs, no retries. The two Python packets use source facts
from verified pre-fix parents of document and facade changes; the Rust,
C/C++, and Bash packets are synthetic. Provide only pre-change snapshot facts
and the applicable instruction excerpt. The evaluator cannot inspect later
repairs, sibling outcomes, or the scoring rubric. Run cases in read-only mode.
Retain raw prompts and responses privately; publish a concise report containing
the exact revisions, harness/model versions, observed choices and failure modes,
elapsed time, and limitations. The fixture generator only writes deterministic
local case files outside the shipped skill tree.

### Failure model

Count as evidence only a named owner, affected callers, obsolete path disposition,
protected-contract decision, and verification plan traceable to a packet. A
merely repeated rubric phrase cannot pass. Mark missing output, noncompletion,
and ambiguous evidence as failed or inconclusive, never as a success. A
historical repair is context for constructing a packet, not its required answer.
No benchmark service, telemetry, automatic repair authority, or sibling rule
change belongs here.

## Success

The report records each baseline/revised decision for Python, Rust, C/C++, and
Bash. It distinguishes coherent consolidation, justified retention, clean
extension, unrelated cleanup refusal, and a protected-contract checkpoint.
It identifies missed migrations and gratuitous changes, including none observed.
Multiple supported designs can satisfy the rubric. A human calibrates the
rubric against example outputs before scoring; disagreements remain visible.

## Validation

- `focused-test`: fixture script creates identical case bytes across repeated
  invocations and refuses overwrite or unknown cases.
- `task-test-not-applicable`: no executable implementation runs in the ten
  design-only evaluator contexts, so repository guardrail results cannot prove
  the proposed migrations. Run `just verify` for this repository change.
- Read the raw outputs against the frozen, calibrated rubric and record every
  attempted run, its elapsed time, and any invalid setup. Source parents and
  snapshot excerpts must match the cited GitHub commits before publication.
